# KRINO 架构图：开源组件候选和首版组合

整理日期：2026-11-02；最近更新：2026-11-04。范围为用户提供图片中可见的 19 个功能框；图片下方被裁切的部分不作推测。

本次更新：补全硬件动作、语言、对话和执行结果进入记忆库的候选与接入链路；增加 MMAction2 动作识别候选，以及 MemoryBank、Generative Agents 的选择性记忆与遗忘机制参考。Smart Memory 仍主要归入第 10 框，并向第 13 框提供状态、与第 19 框存储层衔接。

这是选型候选，不代表已经安装、完成集成或在某款眼镜上验证。根据项目官方仓库和文档整理；没有运行任何哈希、SHA256 或校验和测试。

## 1. 对架构的理解

这张图描述的产品是：眼镜提供视听和传感器入口，手机或边缘设备负责实时显示、连接和简单检测，KRINO Core 维护角色状态并协调体验，后端提供语言、语音、视觉和存储能力。

“乐高积木”这个理解可用，但每块之间需要你们规定接口。库可以提供传感器处理、推理、渲染、工作流和数据库；你们的产品代码负责把“角色是谁、看到了什么、现在做什么、实际做成了什么、以后记住什么”连接起来。

Cloud / Backend 是逻辑上的服务层，可以运行在用户电脑、自建服务器或团队托管服务器上，不必都在公有云。KRINO Evaluator 是图中的自定义模块名称，本文没有把它当作已经存在的同名开源模型。

| --- | --- | --- |
| 1. AR 显示／投影模组：Waveguide / MicroLED / HUD | [OpenXR SDK](https://github.com/KhronosGroup/OpenXR-SDK)：OpenXR 接口头文件和 loader。[Godot OpenXR Vendors](https://github.com/GodotVR/godot_openxr_vendors)：在支持的运行时接入厂商扩展。 | 光波导、显示屏、光机属于采购或代工的硬件。先选能提供渲染入口和所需跟踪能力的眼镜，再选引擎。OpenXR SDK 不会让任意眼镜自动支持 AR。 |
| 2. 按键／触控／唤醒 | [Zephyr](https://github.com/zephyrproject-rtos/zephyr)：自研板卡时可用的嵌入式系统及硬件驱动框架。[sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx)：关键词检测，可用于语音唤醒。 | 现成眼镜优先读取厂商 SDK 的按键、触控事件；不用为了按键识别训练模型。自研 MCU 才考虑 Zephyr，并按芯片选驱动。统一输出 `wake`、`tap`、`long_press` 等事件。 |

| 4. 摄像头 Camera | [CameraX](https://developer.android.com/media/camera/camerax)：Android 摄像头预览、图像分析等；[OpenCV](https://github.com/opencv/opencv)：图像处理、标定、特征等。 | CameraX 适用于系统开放的摄像头接口。眼镜摄像头是否可读、是否提供原始帧，要看厂商 SDK；接入后再做缩放、采样和检测。 |
| 5. 麦克风 Mic | [Oboe](https://github.com/google/oboe)：Android 高性能音频输入／输出。[miniaudio](https://github.com/mackron/miniaudio)：跨平台音频采集和播放。 | Android 原生音频可选 Oboe；桌面原型可选 miniaudio。若引擎或厂商 SDK 已能稳定采集，就复用现有接口。它们负责拿到声音，不负责识别句子。 |
| 6. 扬声器／开放式音频 | [Oboe](https://github.com/google/oboe) 或 [miniaudio](https://github.com/mackron/miniaudio)：播放音频、管理输出流。 | 将 TTS 音频送到当前耳机或扬声器即可。还要在语音会话层处理回声和打断，避免角色把自己的声音再次当成用户发言。 |

对于“角色站在房间某处、用户走动后视角发生变化”的体验，硬件需要提供可靠的位置和朝向跟踪，即通常所说的 6DoF。只有朝向的 3DoF 设备，更适合随视野显示；不能仅靠增加渲染库获得稳定的房间定位。

## 4. KRINO Core：4 个模块

| 编号和图片模块 | 开源候选及用途 | 首版建议和接入工作 |
| --- | --- | --- |
| 10. Memory & Persona：人格／记忆／关系状态／世界观 | [Smart Memory](https://github.com/senjinthedragon/Smart-Memory)：分层记忆、关系历史、角色和世界状态、逐角色认知；[LangMem](https://github.com/langchain-ai/langmem)：提取、合并、更新和检索记忆；[trustcall](https://github.com/hinthornw/trustcall)：通过结构化提取和 JSON Patch 更新已有资料；[Graphiti](https://github.com/getzep/graphiti)：可选的时间关系图和来源追踪。选择性记忆另参考 [MemoryBank](https://github.com/zhongwanjun/MemoryBank-SiliconFriend) 和 [Generative Agents](https://github.com/joonspk-research/generative_agents)。 | Smart Memory 原生为 SillyTavern 扩展，自有平台需移植逻辑或拆为服务；独立实现也可采用 LangMem 所需能力。将硬件、语音和聊天的结构化事件送入一套主记忆流程，再执行提取、更新与检索。时间衰减、重要性保护和召回强化由同一策略层协调；详见第 6 节。 |
| 11. Perception Layer：多模态理解 | [MediaPipe](https://github.com/google-ai-edge/mediapipe)：低层姿态／手部等信息；[MMAction2](https://github.com/open-mmlab/mmaction2)：视频或骨架动作识别；[Qwen3-VL](https://github.com/QwenLM/Qwen3-VL)：图片、视频的语义理解。 | 将语音转写、姿态和视觉描述合成统一场景状态。保留观测、用户自述和模型推断的来源差异。动作识别需选择类别并适配数据；眼镜视角未必能看到用户全身。VLM 不代替设备空间跟踪，融合层需自己编写。 |
| 12. KRINO Evaluator：高速决策模型 | [XState](https://github.com/statelyai/xstate)：规则、状态和事件决策的参考；可选 [Qwen 小模型](https://github.com/QwenLM/Qwen3) + [llama.cpp](https://github.com/ggml-org/llama.cpp)，配合 [Outlines](https://github.com/dottxt-ai/outlines) 输出受约束的结构。 | 首版先用规则做响应优先级、打断、动作选择。只有无法规则化的意图分类等任务才调用小模型。XState 是 JS／TS 运行库；Python 或引擎端可以实现同等状态逻辑，不必增加一个服务。Outlines 约束格式，不保证决定正确。 |
| 13. Experience Orchestrator：体验编排／剧情触发 | [XState](https://github.com/statelyai/xstate)：事件、角色状态和流程切换；[LangGraph](https://github.com/langchain-ai/langgraph)：Python 中可恢复、有状态的模型工作流；[Pipecat](https://github.com/pipecat-ai/pipecat)：语音和多模态实时管线。[Smart Memory](https://github.com/senjinthedragon/Smart-Memory) 的场景历史、未完成目标和剧情线可为编排提供依据。 | 体验调度和语音管线可配合使用；不必三个框架全部安装。Smart Memory 提供记忆和剧情状态，实时动作与语音调度由本框实现。你们定义什么时候说话、动作何时开始、用户打断后取消什么、什么时候写记忆。LangGraph 不负责逐帧动画。 |

人格编辑界面还可以参考 [CharacterVault](https://github.com/spaceman2408/CharacterVault) 的角色卡编辑、世界书和版本管理。它是 GPL-3.0 的编辑器项目，可以借鉴界面和数据组织；它本身不等于“会持续成长的角色大脑”。

建议人格和记忆至少拆为：公开角色模板、角色长期特征、用户偏好、用户×角色的关系状态、经历事件、当前场景。公开模板能共享，不意味着每位用户的私人互动记忆要进入公共库。

### Smart Memory：第 10 框的重点候选

[Smart Memory 官方说明](https://github.com/senjinthedragon/Smart-Memory)列出了长期事实、会话记忆、滚动摘要、关系历史、角色与世界状态、场景历史、未完成剧情线，以及逐角色区分知识和秘密等功能。它还支持一对一和群聊中的独立角色记忆，适合参考你们未来 AI 酒馆的记忆组织方式。

在本架构中，它主要承担“把互动整理成角色可使用的记忆与状态”，然后把相关内容交给对话模型和体验编排器。第 13 框利用这些信息决定如何继续互动；第 19 框负责持久保存和检索。官方将 Smart Memory 与 SillyTavern 的向量存储作为互补层使用。

对你们最有价值的三个设计是：

- 分层记忆：长期事实、当前会话细节、滚动摘要分别管理，避免把所有聊天不断塞进上下文。
- 可更新的关系和状态：保存关系变化、当前目标与情绪等信息，让后续回答有连续性；这些提取结果仍需要允许用户纠正。
- 每个角色分别知道什么：AI 与 AI 互动时保留参与者、旁观者与信息来源，区分亲历和转述。

自有平台的接入工作建议为：

1. 适配会话和角色标识。它原生依赖 SillyTavern 的扩展环境；需要迁移相关逻辑，或拆出独立的记忆服务，再接你们的聊天与模型接口。
2. 增加实际互动事件入口。将 `action_completed`、`action_interrupted`、`action_failed` 及客户端确认的音频播放进度整理成可追溯事件，供记忆模块使用。这是你们需要新增的适配，不能只根据聊天里写了什么判断动作是否发生。
3. 适配存储与隔离。将用户、角色、会话、来源和时间等字段接到自有持久层；Postgres／pgvector 接入需要实现适配，并保留公开模板与私人记忆的边界。
4. 选择一套主记忆流程。可移植 Smart Memory 的逻辑，也可参考它的数据组织后用 LangMem 等实现；先确定谁负责提取、合并、检索和注入，避免多套组件重复写入。

首版建议优先参考其长期／会话／摘要分层、关系状态和记忆编辑功能；复杂剧情线及逐角色秘密可以随后加入。角色初始设定、人格成长规则、AR 动作执行和语音同步仍由你们的产品层负责。

## 6. 跨模块组件与记忆更新候选

### 语音会话：图中需要明确安排职责

STT 和 TTS 之间还需要有人负责会话：判断用户何时说完、是否在打断、停止旧音频、取消旧生成，以及回声处理的接入。

- [Pipecat](https://github.com/pipecat-ai/pipecat)：适合将 STT、LLM、TTS 和自定义事件处理拼成管线。
- [LiveKit Agents](https://github.com/livekit/agents)：适合连同 WebRTC 连接、房间和客户端会话一起搭建；可自托管。和 Pipecat 作为首版主框架时通常择一，具体传输也可以另行组合。
- [Silero VAD](https://github.com/snakers4/silero-vad)：检测是否有人说话；不负责把声音转成文字。

回声消除应在音频采集／传输链路处理，不能靠提示词解决。用耳机、骨传导还是扬声器，主要改变输出路由和回声环境，不要求更换整个角色系统。

### 角色前端：跨模块的产品参考

[AIRI](https://github.com/moeru-ai/airi) 是很值得参考的整体项目，涉及虚拟角色、语音和模型接入。它可用来研究“角色如何呈现和说话”，不代表直接具备眼镜的空间定位及房间交互能力。

### 使用硬件时的动作、语言和对话，怎样进入记忆

本节面向当前的 AR 眼镜和音频硬件。此前文档已经说明执行回报应进入记忆，但还没有逐环节列出完整候选。建议用事件适配器把采集、对话、动作执行和记忆管理连接起来；以下项目分别提供其中的可复用能力。

| 环节与对应框 | 候选 | 可复用能力 | 你们要补的接口 |
| --- | --- | --- | --- |
| 用户动作与手势：第 3、9、11 框 | 设备跟踪 SDK + [MediaPipe](https://github.com/google-ai-edge/mediapipe)；复杂动作可选 [MMAction2](https://github.com/open-mmlab/mmaction2) | 获取姿态、手部等信息，或从视频／骨架序列识别指定动作。 | 把传感器数据归并成有起止时间、主体与置信度的事件；依据相机视角选择能识别的动作类别。连续 IMU 帧可先在本地处理，挑有意义的变化进入记忆流程。 |
| 用户说了什么：第 5、15 框 | [FunASR](https://github.com/modelscope/FunASR) 或 [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) | 语音识别；部分模型与运行方式支持流式转写。 | 记录说话者、语句 ID、时间、转写版本与最终结果；流式中间文本用于即时响应，最终文本再形成稳定记忆证据。 |
| 对话、打断与语音状态：第 13、17 框 | [Pipecat](https://github.com/pipecat-ai/pipecat) 或 [LiveKit Agents](https://github.com/livekit/agents) | 组织实时语音管线、会话事件和模型／工具调用。LiveKit 的[事件文档](https://docs.livekit.io/reference/agents/events/)列有转写、对话条目、打断标记与语音播放跟踪入口。 | 收集用户与角色的消息，关联消息和播放／打断事件；另接客户端播放进度。生成音频、服务端发送音频和客户端确认播放分别记录。 |
| 角色实际执行了什么：第 8、13 框 | Godot／Unity 动画执行器 + 厂商 SDK 回调；这一段由你们适配 | 复用引擎动作状态和完成通知，接收设备可提供的状态回报。 | 统一记录请求、开始、完成、被打断和失败。区分用户动作与虚拟角色动作，用同一个交互 ID 关联，而不是依据生成的台词推断执行结果。 |
| 从交互中提取事实和更新档案：第 10 框 | [LangMem](https://github.com/langchain-ai/langmem) + 按需使用 [trustcall](https://github.com/hinthornw/trustcall) | 提取、合并和更新记忆；用结构化字段或 JSON Patch 修改资料。 | 将已整理的对话和事件作为输入，定义经历、偏好、关系变化和当前状态的结构，保留证据事件 ID；决定哪些候选事实需要用户确认。 |
| 角色分层记忆与关系历史：第 10 框 | [Smart Memory](https://github.com/senjinthedragon/Smart-Memory) | 长期／会话／摘要分层、关系状态、旧事实替换和按角色区分认知。 | 自有平台要适配其 SillyTavern 环境依赖，再将硬件与播放事件接入。与 LangMem 路线选择一套主流程，或明确分工，避免重复写入与互相覆盖。 |
| 随时间变化的事实与关系：第 10、19 框 | [Graphiti](https://github.com/getzep/graphiti) | 按事件增量建立时间关系图，保留事实的有效期与来源。 | 将共同经历整理成带参与者和时间的事件，配置模型、嵌入模型及图数据库，并实现用户／角色隔离；作为复杂关系查询的后续候选。 |
| 保存和召回：第 19 框 | PostgreSQL + [pgvector](https://github.com/pgvector/pgvector)，或独立 [Qdrant](https://github.com/qdrant/qdrant) | 保存事件与记忆，按条件和语义查找相关内容。 | 通过事件 ID、唯一约束和写入状态处理重复通知与失败重试。记忆评分、合并与遗忘由第 10 框控制。 |

这里的“动作识别”与“记忆更新”需要通过你们的接口连接。例如 MMAction2 能提供视频理解算法，LangMem 能提供记忆处理能力；目标动作的类别、证据格式以及它应当改变哪一项角色资料，由你们定义。

建议先落地下面这条异步写入链路，让显示和实时对话持续运行：

```text
眼镜姿态／手势 + 最终语音转写 + 应用内文字消息
    + 虚拟角色动作回报 + 客户端语音播放回报
    → 统一事件：主体、来源、时间、状态、置信度、交互 ID
    → 按一次互动归并与整理
    → 记忆提取器生成候选事实、经历摘要和状态变化
    → 合并、纠正、判断重要性和有效期
    → 写入第 19 框，更新第 10 框角色资料
    → 下次互动按相关性和记忆策略召回
```

下表是产品接入示例，属于建议设计，不是上述项目自带的完整眼镜功能：

| 输入证据 | 可以更新的记忆 | 处理方式 |
| --- | --- | --- |
| 用户明确说“以后叫我阿林”，语音最终转写或文字消息已确认 | 用户希望使用的称呼 | 写入用户×角色资料，并关联原消息；有新指示时更新。 |
| 检测到挥手，同时用户说“我回来了” | 本次互动中的问候事件 | 记录为共同经历或会话摘要；一次动作不直接推导长期性格。 |
| 角色动作已开始，用户随后打断，播放器回报语音只播放了一部分 | 本次动作和对话的实际进展 | 保存打断结果和已确认播放的范围，未完成部分仍保持未完成状态。 |
| 用户多次明确表示某种互动方式更合心意 | 可持续使用的偏好 | 经确认后提高保留优先级；保留每次证据来源，允许以后修改。 |

### 选择性记忆与遗忘：开源候选

这些机制管理的是模型外部的记忆。模型每轮读取最近对话、角色资料和选出的相关回忆；上下文额度仍有限，记忆策略负责安排哪些内容进入这一轮。

| 候选与形态 | 已有机制／研究思路 | 放置 section | 首版用途与接入程度 |
| --- | --- | --- | --- |
| [Smart Memory](https://github.com/senjinthedragon/Smart-Memory)：SillyTavern 扩展 | 重要性、持久程度、召回情况等评分；重复记忆合并；新事实替代旧事实；按预算挑选上下文。其[评分代码](https://github.com/senjinthedragon/Smart-Memory/blob/main/memory-utils.js)可直接阅读参考。 | 主要第 10 框，连接第 13、19 框。 | 优先参考角色记忆组织和筛选；可在 SillyTavern 体验，自有平台需移植。上下文筛选、存储数量裁剪和旧事实退役分别处理，不能都称为按时间自动删除。 |
| [MemoryBank／SiliconFriend](https://github.com/zhongwanjun/MemoryBank-SiliconFriend)：论文配套研究代码 | [论文](https://arxiv.org/abs/2305.10250)提出参考遗忘曲线，让记忆随时间衰减，并通过回忆强化记忆。 | 第 10 框的衰减／强化策略；由第 19 框保存强度与时间等字段。 | 适合参考算法并适配现有模型和存储。原实现含随机移除记录的路径；首版可自行设计为先降低召回权重或归档。公式实现需先修正，见下文。 |
| [Generative Agents](https://github.com/joonspk-research/generative_agents)：角色模拟研究框架 | [论文](https://arxiv.org/abs/2304.03442)中的记忆检索综合近期性、重要性和相关性，并将经历整理为更高层的反思；可查看其[检索实现](https://github.com/joonspk-research/generative_agents/blob/main/reverie/backend_server/persona/cognitive_modules/retrieve.py)。 | 记忆与反思主要放第 10 框；产生的目标和计划供第 13 框使用。 | 参考选择回忆和从经历形成长期认识的结构，适合未来 AI 酒馆；迁移时重新校对评分与时间定义，按你们的事件接口实现。 |
| [LangMem](https://github.com/langchain-ai/langmem)：记忆开发库 | 提取重要信息、后台合并更新、记忆检索及可自定义的存储接口。 | 第 10 框，连接第 19 框。 | 适合用来搭建你们自己的主记忆流程；时间衰减、重要性保护和过期策略需要另行定义。 |
| [Graphiti](https://github.com/getzep/graphiti)：时间关系图框架 | 事实有效时间、来源关联和增量更新，便于保留“以前成立、现在已经改变”的历史。 | 第 10、19 框。 | 适合状态变化和关系历史；重要性遗忘策略另行实现，图数据库按需引入。 |

MemoryBank 的具体实现问题：本次只读检查发现，[`forgetting_curve`](https://github.com/zhongwanjun/MemoryBank-SiliconFriend/blob/main/memory_bank/memory_retrieval/forget_memory.py) 写为 `math.exp(-t / 5*S)`。在正时间下，这会让强度 `S` 越大、保留概率越低，与函数注释“强度越高、遗忘越慢”的含义相反。将其作为算法参考时，需要修正并重新验证衰减逻辑；本文未安装或运行该项目。

建议产品中把下列几种“遗忘”明确分开。这是你们的策略设计，可以复用候选的部分实现：

| 机制 | 用户体验与存储行为 |
| --- | --- |
| 重要性保护 | 角色核心设定、用户明确固定的重要事项持续保留；收到明确修改时再更新。重要性取决于内容与用户指示，不能只看发生多久。 |
| 时间衰减与提示召回 | 普通闲聊逐渐降低主动召回优先级，但保留可检索记录；用户给出线索时可以重新想起。 |
| 巩固和摘要 | 相似的日常内容合并为习惯或阶段总结；重要共同经历保留概要，细节按需要压缩。 |
| 到期与事实替换 | 当前场景、临时安排结束后退出活动上下文；变化的偏好或关系保留时间版本，召回当前有效状态。 |
| 归档与永久删除 | 归档内容平时少召回，仍可查询；永久删除另设明确操作，并处理原事件、派生记忆及索引中的对应记录。 |

强化规则建议区分“检索过”与“得到新证据确认”：检索可暂时增加可访问性，用户再次确认或真实事件重复发生才提高事实的可信程度。角色自己反复提到同一件事，不应自动变成新的证据。具体权重和衰减速度通过产品实验确定。

首版只选一套主流程：可移植 Smart Memory 的分层和评分逻辑，或用 LangMem／trustcall 自行实现；借鉴 MemoryBank 的时间衰减与 Generative Agents 的召回／反思结构，按需加入。这样可以把“互动会更新记忆”和“琐事逐渐淡忘、重要经历长期保留”放进同一套策略中。

## 7. 如何让积木真正拼得上

建议你们拥有自己的事件协议，组件通过适配器接入，不直接依赖某家模型的私有返回结构。

| 接口 | 建议内容 | 用处 |
| --- | --- | --- |
| 感知事件 | `event_id`、`session_id`、`interaction_id`、主体、时间、来源、类型、内容、置信度 | 将按键、语音、视觉和设备跟踪送到同一套处理流程，并关联同一次互动。 |
| 角色状态 | `character_id`、公开模板版本、当前状态、关系状态、可用动作 | 更换模型或设备后仍能延续角色。 |
| 动作请求 | 动作 ID、目标、参数、开始条件、可否打断 | 大模型提出意图，本地执行器落实动作。 |
| 执行回报 | 请求 ID、主体、已开始／已完成／被打断／失败、时间、播放进度或动作结果 | 让编排器知道已确认的执行进展，并区分用户动作和虚拟角色动作。 |
| 记忆写入 | 用户、角色、证据事件 ID、发生时间、事实内容、置信度、重要性、类型、有效状态 | 保留可追溯的互动记忆，支持纠正、合并及事实更新。 |
| 记忆策略 | 持久类别、记忆强度、最后召回／确认时间、到期时间、固定标记、替代关系 | 支持选择性召回、衰减、强化、过期与归档。字段和规则由你们定义。 |

另外约定坐标系、米或厘米、时间基准、音频采样率和格式、动作名称及版本。Unity/C#、Godot/GDScript、Python、TypeScript 之间通过接口连接，不能直接把不同语言的库当作一个包导入。

你们的关键回路建议是：

```text
用户说话／设备事件
    → 场景状态 + 角色状态 + 相关记忆
    → Evaluator 判断优先级和意图
    → Orchestrator 安排语音和动作
    → 本地角色执行器播放，音频设备实际发声
    → 回报完成／打断／失败
    → 整理事件并更新记忆
```

例如角色准备做一个动作，但用户打断了，记忆要保留“被打断”的实际结果。语音同样要区分已生成的文本、已发送音频和客户端确认播放的内容。AI 和 AI 的场景也保留参与者和来源，避免混入用户亲历记忆。

## 8. 低成本首版组合

以下是建议，不是已经选定或验证的依赖清单。

| 部分 | 优先组合 |
| --- | --- |
| 显示和跟踪 | 先使用有 SDK、能输出所需姿态的现成设备。硬件支持时走 Godot + OpenXR + godot-vrm；若厂商主要支持 Unity，则用厂商 SDK + Unity + UniVRM。 |
| 事件和动作 | 本地简单状态机 + 少量固定动作 + 执行回报；先接好打断和持续显示。用户动作优先用 SDK／MediaPipe 的少量明确事件，MMAction2 留作复杂识别候选。 |
| 语音 | Pipecat + FunASR 或 sherpa-onnx + CosyVoice；模型和运行位置按目标机器实测选。收集最终转写、对话、打断和客户端播放进度。 |
| 角色和记忆 | 自有结构化角色资料 + 一套主记忆流程 + PostgreSQL / pgvector。可移植 Smart Memory，或用 LangMem／trustcall 自行实现；先加入重要性筛选、摘要、临时状态到期与可归档的时间衰减。MemoryBank 和 Generative Agents 提供机制参考，不要求整个框架一起部署。Markdown 保留为可编辑导出／备份。 |
| 互动写入 | 自有事件适配器将动作、语句、播放与执行回报按交互 ID 归并，异步提取并合并记忆；通过事件 ID 与数据库唯一约束处理重复写入。 |
| 对话 | 一款合适规模的 Qwen + llama.cpp；托管 GPU 服务时可换 vLLM。 |
| 视觉 | 设备跟踪 + 少量 MediaPipe 检测；Qwen3-VL 先按需启用。 |
| 后端 | 扩展已有 API；Python 路线可用 FastAPI。链路稳定后再加入更完整的观测。 |

第一轮原型先验证一个闭环：用户能持续看见角色，能自然说话并打断，角色能响应并执行少量动作；一次互动的语句和动作结果能形成可查看、可纠正的记忆，退出重进后仍能召回关键经历。记忆策略应能区分核心信息、可压缩日常与到期状态。随后才扩大动作库、复杂场景理解、图记忆和 AI 酒馆。

## 9. 开源属性中影响选型的几处区别

- Godot 相关开源代码和设备厂商 SDK 是两回事。Godot OpenXR Vendors 主体为 MIT，部分厂商组件单独授权。
- [Unity AR Foundation Samples](https://github.com/Unity-Technologies/arfoundation-samples/blob/main/LICENSE.md) 使用 Unity Companion License；不能把这一整条路线描述为完全开源引擎。
- [godot-vrm](https://github.com/V-Sekai/godot-vrm/blob/master/LICENSE) 的代码为 MIT，示例角色模型另有各自许可。代码、角色模型、动作、音色素材分别管理。
- [OpenVINS](https://github.com/rpng/open_vins) 为 GPL-3.0；[CharacterVault](https://github.com/spaceman2408/CharacterVault) 为 GPL-3.0。选择时考虑整个项目的发布许可如何配合。
- [Smart Memory](https://github.com/senjinthedragon/Smart-Memory) 标注 AGPL-3.0，且为独立的第三方 SillyTavern 扩展。直接复用其代码时，将这一许可纳入项目选型和发布安排。
- [MemoryBank／SiliconFriend](https://github.com/zhongwanjun/MemoryBank-SiliconFriend/blob/main/LICENSE) 的代码许可为 MIT；其旧模型、数据与外部依赖分别核对。MMAction2 的代码与使用到的预训练模型、数据也分别管理。
- 推理框架开源，不意味着它加载的所有模型权重都用相同许可。[FunASR](https://github.com/modelscope/FunASR) 明确区分工具代码和预训练权重；[LiveKit Agents](https://github.com/livekit/agents) 框架和其 turn detection 模型也分别授权。

这些候选解决的是通用能力。你们需要自己保有的产品层是：人格和记忆的数据定义、记忆如何改变角色行为、语音和动作如何共同编排、以及实际互动如何反馈到角色成长。
