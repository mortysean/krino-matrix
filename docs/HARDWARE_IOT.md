# KRINO GLASSES 硬件与物联网设计（第一版草案）

2026-11-14 起草，2026-11-15 修订：Krino glasses 有屏幕，角色出现在这副眼镜的显示里。草案，未评审。标了“需核实”的地方，是我手上没有一手资料的芯片参数、价格和腾讯云能力，下单或立项前要找原厂 / 腾讯云确认。

## 0. 结论

1. **Krino glasses 有屏幕，角色出现在这副眼镜的显示里。** 屏幕还没开始做。桌上的 ESP32-S3、麦克风、功放和扬声器只跑语音。角色是彩色形象，要彩色空间显示；光波导上的单色字幕不够。显示软件先在 XREAL 上做，光学模组以后做进 Krino glasses 自己的镜片。XREAL 是显示原型，不是另一条产品。
2. **硬件不从零画光学**：语音原型用 ESP32-S3，1～2 个月跑通对话。显示原型用现成 XREAL，把角色和空间锚点跑通。量产用有屏方案：音频仍是双芯片（主 SoC 加低功耗音频 / 蓝牙 SoC），另外加彩色微显示和光学模组。我们做 ID、显示与语音的上层和云端。
3. **物联网分两个平面**：腾讯云物联网开发平台（IoT Explorer）只管控制面，包括设备身份、绑定、物模型、OTA 和日志。音视频这条媒体面走我们现有的 `/api/devices/ws`，不走 MQTT。
4. **GAAP 先不买**。海外版的对话本来就走 OpenRouter / OpenAI，不经过国内 GPU。现在跨境的只有东京到算力服务器的 SSH 隧道。先花 250 元/月把东京带宽扩到 10 Mbps。只有决定让海外用户用国内 GPU 时才上 GAAP，而且源站要放在杭州服务器上，不能放在算力服务器上（第 5 节）。

## 1. 参考：Meta 与 XREAL 各给了什么启发

| | Ray-Ban Meta（无屏） | Meta Ray-Ban Display / Orion（有屏） | XREAL（Air 2 Ultra / One 系列 + SDK） |
| --- | --- | --- | --- |
| 形态 | 普通眼镜外观，摄像头、开放式扬声器、多麦克风 | 单眼显示加 EMG 腕带 | 有线连接手机或 Beam Pro 的显示眼镜 |
| 算力 | 镜腿里一颗 SoC（Snapdragon AR1），重活交给手机 App 和云 | 同上，加腕带 | 计算在宿主（Android），眼镜只负责显示和追踪 |
| 我们学什么 | 重量、续航、隐私灯。这是无屏产品，不是 Krino glasses 的形态 | 有屏能做进眼镜外形。单眼小屏只够文字，放不下彩色角色 | 彩色画面和空间锚点：让她“站在你书桌上”，下次回来还在。现有机型要插线 |

Krino glasses 是有屏的 AR 眼镜，赛道是陪伴，屏幕用来让数字生命在场。Rokid Glasses 是同一类硬件里能无线、能整天戴的出货第一，它的产品是翻译、导航和提词，镜片上是单色文字和小图标。Krino 参考它的佩戴方式，不参考它的屏幕内容。她要一直在：待机、看向你、说话，都在眼镜本地连续播放。云端只下发表情、语音和要说的话，不逐帧送画面。彩色角色要锁在书桌上，今天仍要一根视频线，那是在场的加强，不是陪伴的起点。平衡见 2.3.1。

## 2. 硬件设计

### 2.1 分三步走

| 阶段 | 形态 | 主控 | 目的 | 周期（估计） |
| --- | --- | --- | --- | --- |
| P0 语音原型 | 桌上，不是眼镜，没有屏幕 | ESP32-S3 | 跑通“唤醒 → 说话 → 她回答 → 拍照她看见”和腾讯云配网、OTA | 1～2 个月 |
| P1 显示原型 | XREAL + 手机或 Beam Pro | Android 宿主上的 Unity | 角色出现在眼前，空间锚点。验证显示软件 | 与 P0 并行 |
| P2 有屏眼镜 | Krino glasses 整机 | 音频方案 + 彩色显示模组（需选型） | 语音和角色显示在同一副眼镜里 | 显示模组选定之后 |

**为什么 P0 没有屏幕**：桌上这批零件是开发板、麦克风、功放和扬声器，驱动不了彩色空间显示。光学、散热和电池留到 P2。P0 和 P1 用同一套后端协议，P1 先把角色画出来。

### 2.2 P0 开发板 BOM（ESP32-S3）

| 模块 | 建议 | 说明 |
| --- | --- | --- |
| 主控 | ESP32-S3（带 8MB PSRAM 的模组，如 ESP32-S3-WROOM-1-N16R8） | Wi-Fi + BLE。乐鑫官方有腾讯云 IoT Explorer 组件（esp-qcloud），也支持腾讯连连配网（需核实当前版本） |
| 麦克风 | 2 颗 MEMS + ES7210 之类的 ADC | 做双麦降噪。唤醒词用乐鑫 ESP-SR / WakeNet |
| 扬声器 | I2S 功放（MAX98357A 一类）+ 小腔体喇叭 | 播放云端下发的 Opus |
| 摄像头 | OV2640 / OV3660（DVP） | 只拍静态照片给 VLM，不做视频 |
| 交互 | 一个按键 + 一颗 LED | 按住说话；LED 指示录音 / 拍照（见 2.4 隐私） |
| 电源 | 500～1000mAh 锂电 + 充电管理 + USB-C | |
| 显示 | 这一版不装 | 角色显示在 P1 用 XREAL，不往开发板上加屏幕 |

音频编码在设备上做（Opus 16kHz 单声道，约 24 kbps）。现在协议里 `mic.audio` 是 base64 放在 JSON 里，体积多 33%，P0 改成二进制帧（第 4.3 节）。

### 2.3 P2 量产方向（有屏）

音频部分的常见做法仍是双芯片（Ray-Ban Meta、小米 AI 眼镜这一类，具体型号需核实）。角色显示是另外的彩色微显示和光学模组，无屏公版里没有。

| 芯片 / 模组 | 职责 | 候选（需核实） |
| --- | --- | --- |
| 主 SoC | 摄像头 ISP、拍照 / 录像、Wi-Fi 上传、跑系统 | Qualcomm Snapdragon AR1 Gen 1；降本可看紫光展锐、全志等国产 AI 眼镜方案 |
| 音频 / 蓝牙 SoC | 常开的蓝牙音频、唤醒词、通话降噪，主 SoC 休眠时工作 | 恒玄 BES2700 / BES2800 系列 |
| 显示 | 彩色画面，放得下角色形象和空间位置 | 鸟浴 / 棱镜一类微显示 + 光学模组。光波导单色小屏只够文字，不够角色 |
| 传感器 | 佩戴检测、IMU（姿态，喂给 `imu.pose`）、触控镜腿 | 6 轴 IMU、电容触控 |

### 2.3.1 便携和画面

角色要站在书桌上，头转开再回来还在原地，画面就要在每次刷新前按最新头部姿态重投影。送进眼镜的是一整帧彩色像素，接法和投屏的 HDMI 是同一类：XREAL 用 USB-C 的 DisplayPort，线同时供电。P1 的 XREAL（含 2026 年 11 月开始出货的 Aura）都是这样，没有无线版。Wi-Fi 传压缩视频会多一截编解码，角色会飘，交互先坏在这里。

Rokid Glasses 能不接线，是因为蓝牙传的是文字和状态，画面在镜腿里画。分辨率和颜色都小，彩色角色放不下。

| 做法 | 便携 | 角色 |
| --- | --- | --- |
| 镜腿自绘，无线 | 能整天戴 | 文字或小图标 |
| 短线到口袋里的手机或计算盒 | 脸上有一根短线，主机在口袋 | 彩色，锁在空间里。P1 用这个把交互验清楚 |
| 算力和电池都塞进镜腿 | 没有线 | 重量、发热、续航一起上来。P2 再量 |

平衡先定成：没有线时，她仍然在场，本地继续待机和看向你。P1 用口袋到眼镜的短线，确认锁在书桌上值不值得。P2 再量这根线能不能缩短或拿掉。拿掉以后可以失去“站在某个位置”，不能变成一块只在说话时亮起的字幕屏。

选型的硬条件：

1. **主 SoC 能跑腾讯云设备 SDK**。跑 Linux / Android 的 SoC 直接移植 C SDK（qcloud-iot-explorer-sdk-embedded-c）或用 Android SDK，不需要认证模组。只有 MCU 级芯片才需要查腾讯云的“认证模组”列表。
2. **能出 Opus 编码的音频流**，最好在音频 SoC 上就编好，主 SoC 不用醒。
3. **摄像头指示灯和摄像头供电硬连**（见 2.4），固件不能单独关灯。
4. **光学模组要能显示彩色角色**，并给出角色在画面里的位置。只做字幕的光波导方案不收。
5. **找有屏方案**：歌尔、龙旗等的无屏 AI 眼镜公版只覆盖音频和摄像头（需询价核实）。显示模组另询有屏方案。我们提供 ID、品牌、显示与语音的上层（KRINO 客户端）和云端，底层驱动、射频、整机认证（3C / SRRC / 海外 FCC / CE）交给方案商。

### 2.4 隐私（硬件层面）

- 摄像头工作时，前置指示灯一定亮，由硬件保证（Meta 也是这么做的，被挡住时拒绝拍照）。
- 镜腿上有物理开关，可以断开麦克风和摄像头。
- 和现有原则一致：画面和音频只在服务端内存里处理，不落盘（见 ARCHITECTURE.md “安全与隐私”）。

## 3. 显示：角色出现在眼镜里

屏幕是为了让她在场，不是为了显示通知。待机、看向你、说话在设备本地连续播放，云端下发表情和语音。P1 在 XREAL 上试她锁在书桌上的效果。这是在场的加强，最终眼镜即使不锁在空间里，角色也不能退回成字幕。

### 3.1 结构

```
XREAL 眼镜 ──USB-C──▶ Android 宿主（手机 / Beam Pro）
                         KRINO Host（Unity + XREAL SDK 3.x）
                           ├─ 渲染角色：动态形象的透明 WebM（motion.py 产出的 chibi）或 Live2D Cubism SDK for Unity
                           ├─ 空间锚点：本地保存 / 加载
                           └─ /api/devices/ws?kind=xreal  ←→ 现有互动流程
```

- 后端新增一个 `DeviceAdapter` 子类 `XrealGlasses`（`kind = "xreal"`），输入输出沿用现有协议。P2 的 Krino glasses 消费同一条 `ar.avatar`：显示从 XREAL 换到自己的光学模组，角色和锚点协议不变。
- 最省事的形象是动态形象任务已经生成的透明 WebM 加 `chibi.json`。它在 Unity 里就是一张带透明通道的视频贴片，不需要另做 3D 模型，也和“为什么不用 3D”的结论一致。
- 注意 XREAL 文档的提醒：开发机先不要升级 Android 16。

### 3.2 空间锚点怎么和现有 `Anchor` 结合

现在 `devices.py` 的 `Anchor` 只能相对头部（yaw / pitch / distance）。扩展成“优先用空间锚点，找不到就退回相对头部”：

```jsonc
// 输出：ar.avatar
{"type": "ar.avatar", "expression": "smile",
 "anchor": {"yaw": 20, "pitch": -5, "distance": 1.5,            // 兜底，和现在一样
            "ref": "a3f…", "offset": [0.0, 0.0, 0.3]}}          // 新增：本地锚点 id + 相对偏移（米，|x|≤3）

// 输入：用户在眼镜里把她“放”在某处并命名
{"type": "anchor.saved",   "id": "a3f…", "label": "书桌", "quality": "good"}
{"type": "anchor.located", "id": "a3f…", "tracked": true}
{"type": "anchor.removed", "id": "a3f…"}
```

- **服务端只存锚点 id、用户起的名字和最后一次定位状态，不存地图数据**。XREAL 的锚点地图保存在设备本地，SDK 本身也不支持云端共享，这对隐私是好事：用户家里的空间数据不上云。
- 偏移限制在 3 米以内，这条按 XREAL 最佳实践来定：超过 3 米误差变大，应该新建锚点。
- 策略层可以加一种行为“回到她的位置”。用户回到书桌前、`anchor.located` 变成 tracked，就可以触发一次轻量的问候（仍然受现有“主动开口至少隔 5 分钟”的硬约束限制）。
- 平面检测用来让她站在地面或桌面上。深度网格（遮挡）放到以后再做。
- 校验照旧：`ref` 只接受这个连接上报过的 id，模型碰不到渲染。

## 4. 物联网设计（腾讯云 IoT Explorer）

### 4.1 两个平面

```
                    控制面（MQTT，小包、可靠）
设备 ──── 腾讯云 IoT Explorer ── 数据同步 / 规则引擎（HTTP 推送）──▶ 后端 /api/devices/iot/*
 │         身份、绑定、物模型、OTA、日志
 │
 └──────── 媒体面（WebSocket，实时音频 / 照片 / AR 事件）──────────▶ 后端 /api/devices/ws?kind=krino-glasses
           设备凭控制面换来的短期令牌连接
```

**为什么音频不走 MQTT**：MQTT 适合“电量 15%”“切换到某个角色”这类小消息。实时语音需要低延迟的流，而且我们已经有 `/api/devices/ws`、流式 TTS（`voice.py`）和整套互动流程，接上去最快。以后要全双工、可打断的实时语音，再评估腾讯云 TRTC 的对话式 AI 方案（需核实）。

### 4.2 物模型（第一版）

| 类型 | 标识 | 说明 |
| --- | --- | --- |
| 属性 | `battery` `charging` `wearing` `fw_version` `volume` `privacy_switch` `character_id` `edition` | `edition` 出厂写死 cn / global，决定连哪套后端 |
| 事件 | `wake` `low_battery` `photo_taken` `privacy_on` `fault` | |
| 行为 | `set_character` `get_ws_token` `reboot` `factory_reset` | `get_ws_token`：后端回一个 10 分钟有效、只能用于这台设备的令牌 |

### 4.3 后端要改的

| 位置 | 改动 |
| --- | --- |
| `models.py` | 新表 `devices`：`user_id`、`product_id`、`device_name`、`edition`、`fw_version`、`bound_at`、`last_seen`。查询带 `user_id`（和其它私人数据一致） |
| `devices.py` | `KrinoGlasses.available = True`。WebSocket 认证除了用户令牌，再接受设备令牌。`hello` 里协商协议版本和能力 |
| `devices.py` 协议 | `mic.audio` 改为二进制 Opus 帧。回复改成流式：`ar.subtitle` 增量加 TTS Opus 分片，不再等整轮跑完（现在 `_handle_input` 返回的是整轮结果） |
| 新文件 `iot.py` | 接收 IoT Explorer 的推送（校验签名），绑定和解绑，下发 `set_character`。腾讯云 API 只在这个文件里调用 |
| `config.py` | `IOT_PROVIDER=tencent|off`、产品 ID、密钥（只在服务端） |
| 测试 | 设备令牌只能连自己的设备；`ref` 锚点只能是本连接上报过的 id |

### 4.4 配网与绑定

1. P0、P1 先用**腾讯连连小程序**配网（BLE 辅助配网），用户扫码把设备绑定到腾讯连连账号。
2. 小程序里跳转登录 KRINO 账号，后端把设备记进 `devices` 表。以后自己的 App 做好了再替换腾讯连连。
3. 出厂烧录一机一密，不用一型一密（防止一台被拆就全部被仿冒）。

### 4.5 国内版和海外版

两个版本是两套独立部署，用户数据不跨境（DEPLOY.md）。设备也按这个原则：

- 国内版：IoT Explorer 中国站加杭州后端。
- 海外版：先确认腾讯云 IoT Explorer 有没有可用的海外地域和合规条款（需核实）。没有的话，海外版换 AWS IoT Core 或自建 EMQX。所以 `iot.py` 里要抽一层 `IotControl` 接口，和 `DeviceAdapter` 的思路一样。
- 设备激活时就按 `edition` 固定连接的平台，不在运行时按 IP 判断（理由和 DEPLOY.md 里“不要在一台服务器上按 IP 跳转”相同）。

## 5. 腾讯云 GAAP 方案：怎么用

### 5.1 方案里对的地方，直接照做

- 先扩东京带宽（1 → 10 Mbps，250 元/月）。这一项和 GAAP 无关，现在的 Live2D、立绘、动态形象 WebM 都从东京这 1 Mbps 出去，本来就该扩。
- 如果上 GAAP，必须用四层 TCP 监听器，不用七层。七层会缓冲 SSE。
- 源站要加就绪门控。模型没加载完时不监听端口，健康检查就会失败、摘掉源站。
- 合并 SSE 分片、精简 chunk 字段。这一点对眼镜和海外弱网都有好处，值得单独做。

### 5.2 方案和我们平台不符的地方

| 方案的假设 | 我们的实际情况 | 影响 |
| --- | --- | --- |
| 门户在日本，AI 推理全在国内机房 | 海外版的对话走 OpenRouter，语音走 DashScope / OpenAI，都不经过国内 GPU。跨境的只有东京到算力服务器的反向 SSH 隧道（18640/18641/18660） | 大部分流量本来就不跨境，GAAP 的收益远小于方案的测算 |
| 源站是机房公网 IP:端口 | 算力服务器在内网，没有公网入口，只靠反向隧道出去 | GAAP 无法直接回源到算力服务器 |
| 只考虑 SSE 文字流（约 9 KB/s 一路） | 隧道里还有图片（image_server）和语音 | GAAP 按当天 1 分钟峰值计费：传一张几 MB 的图就可能把峰值顶到几 Mbps，每 Mbps 每天 130 元 |
| 合规只提“数据出境” | DEPLOY.md 的原则是海外用户的数据不进国内 | 让海外用户的语音进国内 GPU，违反这个原则，隐私政策要改，还要评估 GDPR 等境外法规 |

### 5.3 建议

1. **现在**：只扩东京带宽。海外版的 `HEAR_PROVIDER`、`IMAGE_PROVIDER`、`TTS_PROVIDER` 都保持云服务，不走隧道。
2. **以后如果决定让海外用户用国内 GPU**（比如为了统一音色、降成本）：
   - GAAP 的源站选**杭州服务器**（腾讯云资源，有固定公网 IP），算力服务器继续用反向隧道连杭州（国内段，稳定）。链路：东京 → GAAP 四层 → 杭州 Nginx :8080（proxy_protocol + 就绪门控）→ 隧道 → 算力服务器。
   - GAAP 上只跑语音（流式 Opus 一路约 3～4 KB/s）和文字流，图片和视频不走 GAAP。东京侧给这条路限速，让日峰值不超过预算档位。
   - 隐私政策写明海外数据在中国处理，法务确认后再上。
3. **眼镜量起来以后**：在海外放一台 GPU（东京 GPU 实例或其它海外算力），海外版完全独立。这样最符合两套部署的原则，也是眼镜实时语音延迟最低的方案。
